# When and how a walkthrough is made

## Speaker notes

The walkthrough is made once the sprint is implemented and its gates pass.

It is made before review, because it is the way into the review.

The implementing agent builds it. It knows the design best, and it is accountable for explaining it.

The deck lives in step 9, build, test, and document, with one folder per feature.

It names the exact revision it describes. A stale deck is corrected before approval.

The agent runs the checks, then stops. It does not stage, commit, or push.

An independent reviewer reads the deck and the diff, and adds to the weak-spots slide.

Pablo reads in a fixed order: why, how, parts, risks. He clicks fine print when he wants to.

Revisions, staleness, and tooling follow the presentation lifecycle.

The deck informs the decision. It authorises nothing: not a merge, not a release.
